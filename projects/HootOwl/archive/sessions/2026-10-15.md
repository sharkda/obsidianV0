# claude — what this crash is

**Short version: the app did not break. 台北市's own data file is broken, right now, on their server — and the app chose to die rather than shrug.** This exact crash cannot happen on an iPhone. **A sibling of it can, and that one is a release blocker.**

## 1. Which line actually trapped

The report has no `Application Specific Information`, so the message is missing. The crashing bundle was **still installed on the simulator**, and its UUID matches the report exactly (`61D52AA8-2571-3DC4-A893-E3B2C4A4BAB2`), so this is symbolicated against the real binary rather than guessed:

```
TaipeiObs.doParse(data:hash:hashCheckState:) + 1944
```

Disassembling that address shows it building the string `"tcmsv_alldesc parse "` + `error.localizedDescription`. That identifies it as **the generic `catch`**, not the `keyNotFound` one above it:

```swift
catch{
#if os(macOS) || targetEnvironment(simulator)
    fatalError("tcmsv_alldesc parse \(error.localizedDescription)")
#else
    ffl(error.localizedDescription)
    throw RetrieveError.ParseError(error.localizedDescription)
#endif
}
```

**That branch is simulator/macOS only.** It was the simulator I left running from the 10-14 verification — launched 17:15:47 on 10-14, died 21:53:38 on 10-15, so it survived about 28 hours and then hit the daily feed refresh.

## 2. Why the parse failed — it is not our bug

`https://tcgbusfs.blob.core.windows.net/blobtcmsv/TCMSV_alldesc.json` **is not valid JSON today.** Fetched three times just now:

| Evidence | Reading |
|---|---|
| `Content-Length: 131068`, and exactly 131068 bytes arrive | **Not truncated in transit** — the server sends precisely what it promises |
| Stable `Content-MD5: dfJrD6XY1XnBEgESDALGIQ==`, byte-identical across 3 fetches | **Not intermittent, not a network glitch** — the stored blob is corrupt |
| At char 112259: `"ParkingType" : "C",\n "2000\r\nRule" : [ {` | A **chunk-size marker** (`2000` = 8192 hex) spliced into the middle of the JSON |
| File ends mid-token: `"ChargeableE` | Cut off at 131068 bytes — **128 KiB − 4** |

So whoever generates that file appears to have written a **raw chunked HTTP body straight to the blob** instead of the decoded payload, and truncated it at 128 KiB. **This is upstream of us and nothing in the app can parse it.** Worth knowing for its own sake: it means 台北市's parking descriptions are currently broken for *every* consumer of that feed, not just us.

## 3. What this would have done on a real iPhone

Nothing visible. The `#else` branch throws, and the throw is caught in `Mu1Base.dailyRetrieveFlow()`:

The app keeps running on the previously saved daily norm, so lots and pins still work. **But the failure is logged at `.debug` and nowhere else** — a city feed can go down for days and the app says nothing to anyone, including us.

Directly above the branch that trapped:

```swift

**No `#if`. We cannot patch a shipped app within a day.

A `fatalError` on **network input** is the wrong tool in principle: a remote file we do not control is untrusted input, and untrusted input must never be able to kill the process.

# claude — Jim's question: "if Taipei renames a field, is there just no availability until I ship a fix?"

**No — it is worse than that, and I have to correct what I told you yesterday.** For the **availability** feed the app does not lose data, it **terminates**. I had only read the daily-description path when I wrote the section above; the availability path behaves differently and it is the one that matters.

## 1. Yes, it is all-or-nothing — one field kills the whole payload

I ran this rather than reason about it, because the rules here are easy to misremember:

| Case | Result |
|---|---|
| All keys present | ✅ decodes |
| **A required key renamed** (`availablecar` → `availableCar`) | ❌ `keyNotFound` — **the entire array is discarded** |
| A key that has a **default value** is missing (`availablemotor: Int = 0`) | ❌ **still throws** |
| An **optional** key missing (`ChargeStation: TChargeStation?`) | ✅ decodes |
| **One bad lot out of three** | ❌ **all three discarded** |

> [!warning] The default value does **not** protect you
> `var availablemotor: Int = 0` looks like a fallback. It is not. Swift's synthesised decoder only falls back to defaults for **optional** types; a non-optional with a default still requires the key to be present. So in `ParkAvailableItem`, **`id`, `availablecar`, `availablemotor` and `availablebus` are all mandatory** — only `ChargeStation` is safe to lose.

And because `park` decodes as `[ParkAvailableItem]` in one call, **one malformed lot out of ~1,700 discards all 1,700.**

## 2. 🔴 But it never gets as far as "no data" — it crashes. On iOS. In Release.

`minuteFlow()` is the live availability path — **both cities, roughly every 2 minutes**. It ends like this (`Mu1Base+Ext.swift:221-226`):

```swift
}catch DecodingError.keyNotFound(let key, let context) {
    fatalError("[\(self.id)] Missing key: \(key.stringValue) — Path: \(context.codingPath)")
}catch{
    fatalError("\(self.urlMinutely.absoluteString) \(error.localizedDescription)")
}
```

**Neither is behind a `#if`.** Both ship. So the day 台北市 renames a field, or publishes a corrupt file — **which is exactly what they did to the sibling endpoint this week** — the user's app quits. They reopen it; about two minutes later it quits again. There is no version of this the user can work around, and we cannot reach them faster than App Review.

`minutelyRetrieveFlow()` is the one I looked at yesterday and it is dead code — its only call site is commented out at `Mu1Base+Ext.swift:337`. The live one is `minuteFlow()`, called from `:78` and `:336`.

**新北市 has one too:** `NewTaipeiCityObs.swift:137`, `guard fields.count == 2 else {fatalError(...)}` — unguarded, so an extra column in their CSV crashes every device. The line above it (`:131`) is correctly guarded with `#if DEBUG || targetEnvironment(simulator)` and does `continue` in Release, which is exactly the right shape — so the fix is already demonstrated eight lines up.

## 3. What it *should* do, and what the user would then see

With the `fatalError`s replaced by log-and-throw, a renamed field means the **last good availability stays on screen** and simply ages — `AvailFreshness` walks it fresh → aging → stale through the colours we settled on 10-08, and `Municipal+Cache` holds it for 24h. Pins, lot names, capacities and the map all keep working, because those come from the *daily* feed, which is a separate file.

**So the honest answer to your question is:** with the fix, yes — no *new* availability numbers until you ship a model update, but the app stays usable and visibly tells the user the counts are old. Without the fix, there is no app to be degraded.
